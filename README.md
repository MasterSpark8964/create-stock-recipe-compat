## 前言

本人在游玩「无限模板」整合包时，希望能通过机械动力仓管更方便地为锻造台配方下单，于是围绕这个需求开始了一个 vibe coding 项目。

最初只是想补上锻造台的适配，后来逐步加入了缺料时展开中间配方、按材料批次下单，以及减少无效搜索的优化。这个项目从自己的游玩需求出发，但实现上尽量不绑定某一个整合包，也不修改机械动力原 Mod。

目前它仍是实验性作品。早期基础功能有实测记录，后续递归补料与优化版本主要经过代码检查和编译，尚未完成系统的运行验证。欢迎带着具体配方、版本信息和日志反馈问题，一起把它完善起来。

## 它能做什么

- **从 JEI 请求配方材料**：读取物品输入槽、候选材料与数量，通过 Create 原有物流网络下单。
- **支持锻造配方**：包含模板、基底、添加物；递归锻造按实际输入检查结果及 NBT，不限定原版物品 ID。
- **缺料时展开中间配方**：例如 `A + B → C`，A 缺货且存在 `D + E → A`，可以请求 `B + D + E`。
- **使用已有库存**：考虑已预留材料、候选材料的共享库存，以及初次规划中的中间产物余量。
- **按材料批次计数**：没有物品输出的配方可使用批次模式；也可手动开启全部按批次计数，避免把概率产物的显示数量当成确定产量。
- **区分失败原因**：原料不足、搜索超时、复杂度上限、递归深度和订单物品种类限制分别提示。

**它请求的是材料，不会替你执行中间合成、操作机器或配送流体。**

## 如何使用

1. 在 Create 中搭好有效的仓管、库存链接和打包机网络，确认仓管能看到库存。
2. 在仓管请求界面通过 JEI 选择配方，使用材料转移按钮加入订单。
3. 直接材料不足时，默认尝试递归补料。检查订单中的实际原料后，使用 Create 原有按钮请求包裹。

普通工作台配方在库存足够时保留 Create 原来的处理方式。通过递归展开的订单只包含原料，不附带让 Create 自动合成中间产物的指令。

### 哪些配方会递归展开

| 配方来源 | 递归处理 |
| --- | --- |
| 工作台、锻造台、熔炉、高炉、烟熏炉、切石机 | 在受支持的原版配方类型和接口范围内展开 |
| 模组 / 数据包注册在上述类型下的配方 | 可参与，不按物品命名空间限制；自定义行为仍有兼容边界 |
| 序列组装、粉碎、研磨、机械合成等模组机器工艺 | 不展开；需要直接储备对应产物 |
| 附魔书制作、已识别的盔甲纹饰配方 | 不展开，减少无效搜索；已有库存仍可作为材料 |
| 必需流体或其他非物品输入 | 不支持整单材料转移，不会悄悄漏掉这些输入 |

“递归忽略机器工艺”不等于“不能在 JEI 选择机器配方请求物品材料”：直接选中的配方仍按其 JEI 输入处理。普通装备锻造升级和基底附魔继承保留；纹饰制作不参与递归。

## 配置

配置文件位于客户端实例的 `config/create_stock_recipe_compat-client.toml`。

| 常用选项 | 默认值 | 作用 |
| --- | --- | --- |
| `enableUniversalJeiMaterialTransfer` | `true` | 启用材料转移 |
| `expandMissingMaterials` | `true` | 缺料时尝试递归补料 |
| `maxDependencyDepth` | `16` | 中间配方最大深度 |
| `allowNonItemOutputs` | `true` | 无物品输出时按材料批次下单 |
| `useBatchUnitsForAllRecipes` | `false` | 所有被本 Mod 接管的配方按批次计数 |
| `forceJeiForCraftingRecipes` | `false` | 强制工作台配方也走材料订单路径 |
| `debugLogging` | `false` | 输出排查用的材料与订单日志 |

完整选项、默认限制和调整说明见 [配置文档](docs/CONFIGURATION.md)。**已有配置中的旧值不会被新默认值覆盖。**

## 已知限制

- JEI 必须完整提供物品输入；无法推断隐藏消耗、机器能量、燃料、概率或所有自定义配方语义。
- 递归锻造按标准三槽、每个非空槽消耗一个物品的接口处理；非标准消耗或服务器专有行为不保证兼容。
- 初次加入订单后，展开方案会固定。之后加量按同一方案放大，不会重新规划，也不保证全局最省材料；需重新规划时，移除后重新加入。
- 默认最多 512 个展开材料单位、16 层中间配方；还有库存规模、搜索量、内存和时间等保护。Create 原有的每单 9 种实际物品限制保留。
- 一秒内复用同一请求的昂贵预览失败，减少 JEI 连续重试；实际下单重新计算。协作式超时不能强制打断模组回调，不保证完全无卡顿。
- 相同候选材料数量不一致时取最大值；这可能保守地多请求材料。NBT 展示信息也可能比实际配方要求更严格。
- 其他 Mod 若修改同一仓管转移逻辑，可能冲突。支持某类接口不等于已经逐一验证所有模组。

## 从源码构建

安装 Java 17 并配置 `JAVA_HOME`，首次构建需要联网下载依赖。

```powershell
# Windows：只编译和打包，不运行测试或启动游戏
.\gradlew.bat assemble -x test
```

```bash
# Linux / macOS
sh ./gradlew assemble -x test
```

输出位于 `build/libs/`。`build-local.ps1` 含开发机器上的 Java 路径，其他机器应优先使用 Gradle Wrapper。开发用集成测试源码不进入发布 JAR。
